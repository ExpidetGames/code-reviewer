REFERENCE

  • Vocabulary and open points

Every screen of the app, in the design of the landing page

This page shows what code-review.com looks like and how it behaves, without any code. It holds the design system and all 52 screens of the app, sorted by area.

Matches the app at commit 88476b43 of developmentStatus 21 Oct 202652 screens

What it is

A reading copy of the design. Each screen is drawn as it should look, with real texts from the app, and tells where it lives in the app and who can see it.

What it is not

Not the app. Buttons do nothing and no data is saved. Names, numbers and dates in the mockups are sample data.

Why the look differs from today

The app currently looks like a default component kit. The wanted look is the one of the landing page, so every screen here uses the landing page design: same type, colors, spacing and motion.

How to read it

  • Start with how the app is organized, then look at the design system once, then the screens of the area you care about.
  • Every screen has a short description, its address in the app, who can see it, and the source file in this repository.
  • Links inside a mockup (sidebar, buttons that lead somewhere) jump to the related screen on this page.
  • Use Light, Dark or Auto at the top left to switch the color theme of the whole page. Auto follows your system.
  • Where a screen changes with a setting or a role, the description says so, and variants (empty, error, dialog) are shown as extra screens or extra blocks.

What changed against the app

  • The look: the landing page design everywhere (see design system).
  • The name: the product is called code-review.com, in lowercase. The app still says "Code Reviewer" in its header, titles, texts and mails.
  • The copy rules of the landing page: no hyphens inside sentences, sentence case, direct sentences. Texts keep their meaning.
  • Status is shown with a word and a symbol, never only with color. The landing page has no status colors, so success, failure and waiting differ by fill, outline and icon.
  • Two screens are new: the 404 page and the error page. The app has none of its own today.

How the app is organized

Three frames, and a few roles that decide what a person sees.

1. Bare card

No header and no sidebar: one centered card. Used for sign in, sign up, password reset, email confirmation, invitations and the first run setup.

2. Workspace app

The floating glass nav on top (logo, workspace switcher, user menu). Inside a workspace a sidebar adds Projects and Runs, then Connections, Members and Settings. Pages outside a workspace (Account, Invitations, Create a workspace) have the nav but no sidebar.

3. Admin area

Address /admin, for instance admins only. The same nav, but its own sidebar with three groups: Admin (Overview, Approvals, Runs), Setup (Instance, Sign up, Sign in) and Integrations (Integrations, GitHub App, Mail, LLM keys, Billing, Catalog).

WhoWhat they can do
Signed outOnly the sign in and sign up pages. Every other address leads to Sign in. Before the first setup everything leads to the setup wizard.
MemberSee projects, runs and members. Start a review by hand. Change the settings of a single project. Read the balance and the journal.
AdminEverything a member can, plus: switch projects on or off, change review defaults, connect GitHub and sync, manage the LLM key, add credit and set a monthly limit, invite and revoke Members, remove Members, use the danger zones.
OwnerEverything an Admin can, plus: change roles, rename the workspace, invite any role, remove anyone.
Instance adminSees the Admin entry in the user menu and the whole /admin area. For everybody else /admin is a 404.

Two instance settings change what is shown: single or multi tenant (one workspace, or people can create more) and billing on or off (Billing replaces the Plan tab, a balance banner appears, runs show a price). A workspace can also use our models (managed key) or its own provider key; managed workspaces never see provider or model names.

Design system

Simple code reviews for every GitHub pull request. The interface is flat, monochrome and quiet: one typeface, hairline borders, one slow easing curve, and the product name in lowercase.

Principles

Content fundamentals

  • Write the product as code-review.com, lowercase everywhere, also at the start of a sentence. Never "Code Reviewer". It must never break at its hyphen: keep it in a white-space: nowrap span.
  • All copy is in English. The only exception is the German Impressum text required by law.
  • Voice: plain, direct, second person ("Your pull request is waiting. Again."). Active voice. Sentence case headings, never Title Case On Everything.
  • Real examples. Hero: "Simple code reviews for every GitHub pull request". Primary action: "Start reviewing pull requests". Header action: "Start reviewing". Secondary: "Or host it yourself from GitHub". Questions: "What happens to my code?".
  • Buttons are a verb plus what you get. Never "Learn more" or "Submit".
  • No hyphens inside sentences, headings or labels: rewrite the phrase ("step by step", "open source"). Proper names that contain a hyphen (PR-Agent, code-review.com) are the exception and stay on one line.
  • No orphaned words: a single word never sits alone on the last line. Headings use text-wrap: balance, body copy text-wrap: pretty, and the last two words of a text share a line.
  • No AI clichés ("Elevate", "Seamless", "Unleash", "Game changer"), no exclamation marks in success messages, no "Oops!" in errors. Errors are direct: "Connection failed. Please try again."
  • Inline code in copy is marked with backticks in the source and rendered with InlineCode in Geist Mono.
  • Never invent numbers, customers, logos, testimonials or legal data. Show what is missing with Todo.

Visual foundations

  • Color. Neutral only, two themes that follow the system (prefers-color-scheme). Body text is fg, supporting text muted, grounds page, surface, raised, raised-strong, borders line and line-strong. warm is used for one panel only. todo and todo-surface mark missing content and nothing else.
  • Backgrounds are flat. No gradients in backgrounds. In dark mode the only grounds are #000000, #181818, #1F1F1F, #272727, #313131 and #131209, which are the dark values of page, surface, raised, raised-strong, line-strong and warm.
  • The one gradient is the hero heading: a left to right text gradient hero-from to hero-to, clipped to the text. Never on a background.
  • Type. Geist for everything, Geist Mono only for code. No italics anywhere, nothing heavier than semibold (600). Sizes land on Tailwind's default scale only (hero 60, page-title 48, heading-1 36, heading-2 30, heading-3 24, card-title 18, body 16, small 14, caption 12). Headings use tight tracking (-0.025em). Main buttons are 16px semibold, header buttons 14px semibold.
  • Spacing. Only the spacing-* steps. Main buttons are spacing-75 vertical and spacing-100 horizontal. Sections are spacing-700 high on small screens, spacing-900 from md up, content at most container-page wide, gutters spacing-300 then spacing-400.
  • Radius. Cards and panels radius-2xl, buttons and tiles radius-lg, pills radius-full. For a shape inside another with a gap under 32px, inner radius = outer radius minus gap (16px card with 8px padding gives an 8px inner shape); at 2px or less leave it square.
  • Borders. Always all the way around or not at all, in line (line-strong on controls and badges). Never a border on one side of a card. Dividers inside a frame are the exception for structure (the footer rule, the frame header).
  • Shadows. Rare. shadow-nav under the floating nav pill, shadow-frame under the hero visual. Nothing else casts a shadow.
  • Layout. Hero heading and subheading are capped at container-hero (680px) with line breaks at meaningful points. Cards sit in a 6 column grid on md (three across at 2 columns each, or two across at 3). Hero text is centered; everything below is left aligned.
  • Imagery. The only photograph is the founders portrait, shown inside a surface frame with 8px padding and an inner radius-lg. The hero visual is a stylised pull request built from skeleton bars: it shows the flow of a review, never invented review text.

States

Every interactive element has the full set. Hover: shift fill (bg-muted on the primary button, bg-raised-strong on the secondary) and lift 2px (-translate-y-0.5). Active: scale(0.98), or the lift is removed. Focus: a solid 2px fg outline with 2px offset on every focusable element, which is at least 3:1 on every ground in both themes. Current page: the nav item has aria-current="page" and sits on raised. Loading uses skeletons shaped like the real layout, never spinners. Empty states are composed getting started views. Errors are inline and specific, never alert().

Iconography

Phosphor icons (@phosphor-icons/react), regular weight at 20px in the nav and 24px for large marks, bold or fill for emphasis. Solar and Iconamoon are the only approved alternatives; Material Icons and Material Symbols are never used. Icons inherit currentColor, never carry their own color, and no emoji is used. The logo mark (a check between two code brackets in a rounded tile) is the one custom drawing; use the file in assets/Logos and never redraw it. Its tile is fg and its strokes page; the favicon file swaps these per system theme.

Motion

  • One easing curve for everything: ease-fluid (cubic-bezier(0.32, 0.72, 0, 1)), duration-default 700ms. Never a default or linear transition. Use transition-all duration-700 ease-fluid.
  • Scroll reveal. Content fades up from translate-y-16 blur-md opacity-0 to rest over duration-reveal (1000ms), triggered once by an IntersectionObserver, staggered by delay-100 steps. The hidden start state applies only when JavaScript has marked the document (.js) and never with reduced motion; without JavaScript everything is visible. Never listen to scroll directly.
  • Tagline reveal. Every word starts at 30% of fg and lights up on its own when it crosses a line 40% above the bottom of the viewport, in reading order, 90ms apart.
  • Fluid island nav. A floating glass pill (mt-6, rounded-full, bg-page/70, backdrop-blur-xl). On small screens the hamburger's two lines rotate into an X and the menu opens as a full screen glass overlay (backdrop-blur-3xl, white or black at 80%) whose links slide up from translate-y-12 with staggered delays.
  • Reduced motion: transitions shrink to 1ms and smooth scrolling is off.

Open points

  • 404 and error screens are new in this design. The app has no not-found or error page of its own today.
  • The name in the app (header, titles, texts, mails) still reads "Code Reviewer". Changing it touches the copy modules in app/src/copy/ and the feature messages.ts files.
  • The admin address is /admin while the code folder is called instance-portal.
  • Icons: the mockups use simple stand in strokes. The real set is Phosphor, as on the landing page and in the app.
  • Not drawn: the review skill editor and the model picker rows of Dynamic Review, the add and edit dialogs of the model catalog, the field by field price correction form of the models.dev catalog, and the text of pull request comments (refusal notices). They exist in the app and follow the same components.
  • Error texts: the app has about 35 sentences for run errors and many form errors. The mockups show examples, not the complete list. The code in app/src/runs/error-copy.ts and the messages.ts files is the source.
  • Billing: the sentence "You confirmed that this workspace buys for a business." exists in the code but was not found on any screen.
  • Sample data: all names, repositories, prices and dates are examples. Plan names, rates and the low balance threshold are set by the operator and are not shown.
  • Font: Geist loads from Google Fonts. Offline, the page falls back to the system font and looks slightly different.
