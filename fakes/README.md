# fakes

Fake servers and fixtures that stand in for every external system in automated tests, so no test
ever needs the internet, a real GitHub or a real model. The same fakes are shared by the app tests
(Vitest), the runner tests (pytest) and the end-to-end journeys (Playwright). They speak the real
protocol, so the production client code runs unchanged against them.

## The fake Paddle (`paddle/`): what is verified and what is not

Creating a product and a price follows the field limits of Paddle's documentation (#440): a price's `description` has 2 to 500
characters with a non-blank one, `name` 1 to 150, `product_id` is `pro_` and 26 lowercase letters or digits, `trial_period`
needs a `billing_cycle` and keeps `requires_payment_method` (default `true`), `quantity` is 1 to 999999999 with the maximum not
below the minimum, `unit_price_overrides` has at most 250 entries with unique country codes; a product has a `type`, a non-blank
name and may have an empty `image_url`. What the documentation does not say (the error codes of these refusals) is unverified, like
the other codes below.

Field shapes come from the research of epic #421 (documentation), not from the sandbox. Two things in the fake are
**not Paddle behaviour** and must not be read as such:

- **`price_field_immutable` is our app's policy, not Paddle's.** Paddle documents `PATCH /prices/{id}` as accepting
  `unit_price`, `unit_price_overrides`, `billing_cycle`, `trial_period` and `tax_mode`; whether it locks them once a
  price is in use is undocumented (research S1). The app refuses such a PATCH in the billing client (`updatePrice`,
  before anything is sent). The fake does not enforce it: it accepts the fields, like the documentation says, so a
  test of the guard goes through the client and a bug that bypassed the client would show.
- **Invented error codes.** The research documents the shape of an error (`{error:{type,code,detail}}`, 404, 409,
  429 with `Retry-After`) and a few codes. Every other code the fake answers with was made up and is **unverified**
  until the sandbox contract run (#448): `entity_archived`, `invalid_request`, `request_too_large`,
  `method_not_allowed`, `authentication_missing`, `internal_error`, `injected_fault`, `too_many_requests`,
  `transaction_already_completed`, `subscription_update_when_canceled`, `subscription_update_when_past_due`,
  `subscription_locked_pending_changes`, `subscription_locked_renewal`. So are the `type` values (`request_error`,
  `api_error`) and the 403 for a missing key. The lists are `DOCUMENTED_ERROR_CODES` and `UNVERIFIED_ERROR_CODES` in
  `paddle/errors.ts`; a test fails when the fake answers with a code that is in neither.

**For later issues (#437 and on):** branch on the HTTP status plus the documented constraint (for example "a
subscription cannot change items within 30 minutes of renewal", HTTP 409), not on these code strings, until the
sandbox contract run in #448 has checked the names. `PaddleClientError.paddleCode` carries the string for logs and
diagnosis only.

Rules:

- Dummy values only. No real tokens, keys or private repository data, ever.
- A fake is configured through an environment variable (for example `GITHUB_API_BASE_URL`), never
  through a switch in production code.
- Fakes live here, not in `app/` or `runner/`, because more than one test suite uses them. The one
  exception for now is the pair of fakes of the runner's engine suite (`runner/tests/engine/fake_github.py`,
  `fake_llm.py`): only that suite uses them and the runner's ruff and pyright cover them there; they
  move here when a second suite needs them.
- Fakes are TypeScript or Python files that run as they are (Node 24 strips the types; no build
  step). The app's `format` and `format:check` scripts cover `fakes/`.
