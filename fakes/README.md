# fakes

Fake servers and fixtures that stand in for every external system in automated tests, so no test
ever needs the internet, a real GitHub or a real model. The same fakes are shared by the app tests
(Vitest), the runner tests (pytest) and the end-to-end journeys (Playwright). They speak the real
protocol, so the production client code runs unchanged against them.

`dynamic_git/` supplies reproducible bare Git fixtures (including fork PR refs and orphan heads),
a loopback-only smart HTTP upload-pack fake with dummy installation authentication/provider faults,
and a blocked-preparation process fixture for runner supervision. Python is checked by the runner's
ruff/strict pyright. It invokes only local fixed Git commands, never an external remote or model.

`wire/` holds the generic fakes of the four provider wire formats (#546): OpenAI Chat, OpenAI Responses,
Anthropic Messages and Google's Generative Language API. `formats.py` builds the JSON answer and the
server-sent events of each from one scripted turn and a usage that differs per call (Chat states usage only
for a request that asked for it; Google's `usageMetadata` can be cumulative on every chunk; CRLF line ends;
an error event for a stream that fails after HTTP 200); `upstream.py` is a provider that accepts only the
real key in the real header on the real path and model (faults of a test's choice: a status with a chosen
`retry-after`, a stream cut midway, an error event inside a stream, gzip, error messages that quote the key,
an answer without `Content-Length`, a fault in the usage of every answer: left out, a field nobody can price, a
count that is no count, one that is stated twice with less, one in an order the family never uses (`usage_fault`, #551); framing: a stream re-chunked at arbitrary byte boundaries); `relay.py` is
the smallest key swapping passthrough, which can also pin the model of the job, a reference for the proxy of
#550. The shapes follow the providers' documentation, they are not captured from real providers yet, and the
assumptions are listed in `docs/spike/544-passthrough.md`, section 6. There is no live relay here: the relay
only ever points at the fake. Python, checked by the runner's ruff and strict pyright; no server is started
on import.

Rules:

- Dummy values only. No real tokens, keys or private repository data, ever.
- A fake is configured through an environment variable (for example `GITHUB_API_BASE_URL`), never
  through a switch in production code.
- Fakes live here, not in `app/` or `runner/`, because more than one test suite uses them. The one
  exception for now is the pair of fakes of the runner's engine suite (`runner/tests/engine/fake_github.py`,
  `fake_llm.py`): only that suite uses them and the runner's ruff and pyright cover them there; they
  move here when a second suite needs them.
- Fakes are TypeScript or Python files that run as they are (Node 24 strips the types; no build
  step). The app's `format` and `format:check` scripts cover `fakes/`.

`stripe/` is the fake Stripe API for the billing module (epic #489, issue #500); the official `stripe-mock` is stateless and has
no webhooks, so it does not replace it. The app's client (`app/src/billing/stripe-client.ts`) runs against it unchanged.

- **API.** Form-encoded bodies, Bearer key, `Stripe-Version` recorded. A parameter it does not know is refused like Stripe does
  (`Received unknown parameter: x`), a required one that is missing is named, an unknown object is a 404 `resource_missing`, a
  list is newest first with `limit` and `starting_after`. Ids and times are the same every run (`cus_Fake00000001`).
- **Idempotency.** The same `Idempotency-Key` with the same parameters answers the saved response (with
  `Idempotent-Replayed: true`); with other parameters it answers the `idempotency_error`. Known differences from Stripe:
  the fake saves only **2xx** answers, while Stripe replays the result of any request that began executing (also a 4xx or
  5xx; not a failed validation of the parameters, not a refusal because of a concurrent request), so a repeat of a refused
  request is run again here and replayed there; a saved answer never expires (Stripe: 24 hours) unless a test calls `fake.forgetIdempotencyKeys()`; the fake runs one request
  at a time, so the 409 `idempotency_key_in_use` for a concurrent request with the same key happens only while a `delay` fault holds the
  answer of the first request (the request ran, its answer is on its way; the refusal is not saved). Code that relies on the replay of an
  error must not take the fake as proof.
- **Managed Payments.** A one-time Checkout session with `managed_payments[enabled]=true` is refused when it carries
  `tax_id_collection`, `invoice_creation`, `customer_update`, `payment_method_types`, `custom_text` and the other parameters
  Stripe's documentation lists as unsupported, or a line item without an eligible product `tax_code`. The Stripe sandbox
  itself refused only `payment_method_types` and `custom_text` (2026-10-20); the fake is stricter on purpose, because the
  documentation is what the money depends on. Of the tax codes the sandbox took `txcd_10000000`, `txcd_10103000`,
  `txcd_10103001` and `txcd_10105002` and refused `txcd_99999999`, `txcd_00000000`, `txcd_20030000` and a text that is no
  code (2026-10-21): the fake takes the `txcd_10......` family and refuses the rest with the sandbox's message; which other
  codes are eligible was not probed. The fake takes **any amount from one cent**, and any tax id value of a type it knows
  (Stripe checks the shape per type); a test of the 10 USD floor or of a VAT ID format must not lean on it.
- **Bad days** (`fake.faults`): `dropResponse` (the request ran, the answer is lost: `hang` or `reset`), `failWith` (a 5xx or
  any status), `rateLimit` (429 with `Retry-After`), `delay`, `respondWith` (a raw answer: an oversize body, a redirect).
- **The buyer and Stripe.** `fake.buyer.pay(sessionId, { taxAmount, charged })` pays an open session (the session completes, a
  payment intent and a charge come into being with consistent ids) and makes `payment_intent.succeeded`, `charge.succeeded`
  and `checkout.session.completed`; `buyer.failAsync` makes `checkout.session.async_payment_failed`. `fake.stripe.refund`,
  `failRefund`, `openDispute` and `closeDispute` are what Stripe or the operator's dashboard does on their own
  (`charge.refunded`, `refund.created`/`updated`/`failed`, `charge.dispute.created`/`funds_withdrawn`/`closed`/
  `funds_reinstated`). A refund the app asks for through the API makes the same events, with the request on them.
- **Loopback only.** The fake listens on the loopback (`host`/`STRIPE_FAKE_HOST` may only name one; anything else is
  refused when it starts) and `flush` sends to endpoints on the loopback only: an endpoint at any other host gets nothing
  and its `DeliveryResult` says `refused: "not_loopback"`. "No real network" does not depend on a test being careful.
- **Delivery.** Events wait in the store until `fake.flush(options)` sends them, signed with `Stripe-Signature`
  (`t=<unix seconds>,v1=<hex>,v0=<hex>`, HMAC-SHA256 over `t.body` with the secret of the endpoint), to the webhook endpoints
  the app created through the API; the secret is in the answer to the create (and `fake.secretOf`). Options: `duplicates`,
  `order: "reversed"`, `delayMs`, `eventIds` (a resend), and a `fault` of the signature: `stale_timestamp`, `bad_signature`,
  `two_v1_valid_first`, `two_v1_valid_last`, `altered_body`, `missing_signature`, `malformed_signature`. The signer is written
  out again in `webhooks.ts` and does not import the app's verifier, so a delivery that verifies proves that both follow the
  documented scheme. The real API wants a public https address for an endpoint; the fake takes any http(s) one at create, but delivers to the loopback only.
- **As a process.** `main.ts` (`STRIPE_FAKE_PORT`, `STRIPE_FAKE_API_KEY`) is controlled over HTTP under `/__fake/`: `GET health`,
  `GET events`, `POST pay`, `refund`, `dispute`, `dispute/close`, `flush`, `reset`. The e2e stack runs it for the billing page of a workspace (#505, `app/e2e/billing/`): the app under test is pointed at it with `STRIPE_API_BASE_URL` and `ALLOW_TEST_STRIPE_ENDPOINTS=true` (`app/src/stripe-endpoints.ts`: loopback http only).
