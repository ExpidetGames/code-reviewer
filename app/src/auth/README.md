# Sign in

Two ways in: **email and password**, which always exists (the instance admin that the first-run setup
creates, `src/setup/README.md`), and **GitHub**, which exists while the GitHub App's user authorization is
configured in the admin portal (`src/github-config/README.md`: no environment variable, no separate OAuth app).
[Better Auth](https://www.better-auth.com) runs both and keeps sessions in the SQLite database (tables `users`, `sessions`, `accounts`, `verifications`, created by
migration `20261010123800_create_auth_tables`, plus the columns and indexes later migrations added, see `src/db/README.md`).

## Who may use the instance

Who may have an account is decided when it is made: by the first-run setup (the instance admin), by the sign-up rule for
the sign-up (`src/signup/README.md`) and for the sign in with GitHub (the rule is applied to the **verified primary email
address** GitHub reports, `src/github-signin/README.md`), and by an invitation. The rule is evaluated then, not on every
request, so a stricter rule never locks anybody out. What an account may use is the two gates in front of the app
(`access-gates.ts`, `lookupSession`): its address has to be verified while the instance can send mail (the instance admin
keeps `/admin`; an account that signs in with GitHub only is not asked: GitHub's primary address was verified at the sign in,
and an imported user's placeholder waits for it), and it has to belong to a workspace (the admin is exempt; an account made by
the sign-up or the sign in has none, so it sees no data until it is invited). A refused account is `unverified` or
`no_workspace` in the session lookup: a page goes to `/verify-email` or `/no-access`, a data route answers 403
`email_not_verified` or `no_workspace_access`. Nobody signs up through Better Auth (`emailAndPassword.disableSignUp`, and
the endpoint is not reachable): `POST /api/sign-up` creates an email account, the GitHub sign in creates a GitHub account.

An account without a workspace still reaches the few places made for it (`NO_WORKSPACE_PATHS` in `access.ts`: `/no-access`,
`/invitations`, `/workspaces/new`, `POST /api/workspaces`, `POST /api/invitations/accept`), which is how it accepts an
invitation or creates a workspace (`src/workspaces/README.md`).

A request for a workspace address (`/w/<slug>...`, `/api/w/<slug>...`, `src/workspaces/paths.ts`) is asked one more thing by the
proxy: the role of the person in that slug (`AccessGates.workspaceRole`). No role is the answer of a path that does not exist (the
same marked request as for the files of the admin portal), for a workspace that does not exist and for one the person does not
belong to alike, the instance admin included. The pages and routes check again (`requireWorkspace`, `withWorkspace`).

An invitation link the person came from travels through the sign in: the login page puts the token into the email form and into
the GitHub form (`invitation`), and the GitHub sign in hands `/invitation?token=...` to Better Auth as the callback address, which
Better Auth keeps with its own state. Only a value shaped like a link token is carried, and the only place it leads to is that page.

The refusals of a sign in with GitHub reach the login page as `?error=<code>`:

| Code                       | Meaning                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------ |
| `github_email_unverified`  | GitHub reports no verified primary email for the account                                         |
| `email_not_allowed`        | The verified address is not one the sign-up rule lets in                                         |
| `signup_closed`            | The rule names emails or domains and nothing can verify an address yet                           |
| `email_exists_unverified`  | An account has this address and one of the two is not verified: nothing is linked                |
| `github_identity_conflict` | The account with this address has another GitHub account                                         |
| `check_failed`             | The addresses could not be read (GitHub failed, or the App lacks the Email addresses permission) |
| `github_not_configured`    | The user authorization is not set up                                                             |
| `sign_in_method_disabled`  | The admin switched this way of signing in off                                                    |

The copy never names who is allowed.

### The allow list of the earlier sign in

Before accounts, the GitHub sign in admitted only people named in `ALLOWED_GITHUB_LOGINS` and/or members of
`ALLOWED_GITHUB_ORG`, and bound a listed login to a numeric GitHub id (`allowed_login_pins`). **That no longer decides who
signs in or who is let through on a request.** The variables are still parsed and the files above are kept because the update
to accounts reads the list once to decide who becomes a member of the default workspace: a listed login whose pinned id
matches, or a live organization member (docs/decisions/0001, section 2.11). `syncLoginPinsOnStart` therefore still brings the
pins in line with the list at every start. The separate OAuth app (`GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET`) is
not read at all; sessions that the earlier sign in made stay valid until they expire (30 days).

## Public paths

Everything needs a session except `/login`, `/api/health`, `/api/auth/**` (the callback of a GitHub linking is among them: it needs the session that started it, which it checks itself), `/api/runners/**` (own
token), `/api/webhooks/**` (own signature), `/reset-password` and `/api/password-reset` (the token in a
reset link is the credential), `/forgot-password` and `/api/password-reset/request` (the visitor asks for a link; limits of their own), `/sign-up`, `/api/sign-up`, `/verify-email`, `/api/verify-email/**` (the sign-up and the verification have limits of their own, `src/signup/limits.ts`) and `/invitation` (the page behind an invitation link; the token is its credential and accepting is a POST that needs a session, `src/workspaces/README.md`) and, while the instance is not set up, `/setup` and
`/api/setup/**` (the setup code and the setup session; the setup gate in `src/proxy.ts`, which runs before
this check, answers 404 for them once the instance is set up and 503 `setup_required` for everything
else before that, `src/setup/gate.ts`). The list is `PUBLIC_PATHS` in `access.ts`; a route
that is not on it is protected, including routes that do not exist yet. The test
`protection.integration.test.ts` reads the routes from the file system and fails when a route is
neither listed as public nor as protected there.

## Decisions worth knowing

- `APP_SECRET` (read as `BETTER_AUTH_SECRET` while that deprecated name is the one set) signs the
  session cookie, encrypts the stored GitHub access token and the secrets of the secret store, and signs the `state`
  of the round trips through GitHub (`src/crypto/`). Rotating it signs everybody out and makes the stored tokens and
  credentials unreadable; the portal asks for the credentials again.
- Cookies are `Secure` exactly when `BETTER_AUTH_URL` is https. In production the server refuses to
  start with a plain http address unless it is localhost, because browsers drop `Secure` cookies over
  http and the sign in would loop with `state_mismatch`.
- Sessions last 30 days from the sign in and are not extended by use (the proxy does not set
  cookies, so an extension could not reach the browser).
- No cookie cache: every request checks the session row, so signing out or deleting a row takes
  effect at once.
- `users.github_login` (optional since the workspace migration: a user can exist without a GitHub account, and `users.imported_at` marks users of an installation that existed before accounts) is written from the GitHub profile at every sign in (`overrideUserInfo`) and
  nowhere else (`/update-user` is not reachable). The identity is the GitHub id in
  `accounts.account_id`, so a renamed GitHub account keeps its user.
- The user is the GitHub account (its numeric id), and an address alone never links two accounts. Better Auth links
  an identity to an existing user only if GitHub reports the address as the verified primary one and the user's own
  address is verified (`accountLinking: { enabled: true }` with Better Auth's default `requireLocalEmailVerified`), and
  the GitHub provider has refused every other match first (`src/github-signin/decide.ts`), including a user that has another
  GitHub identity. Better Auth's endpoints for linking and unlinking stay switched off; linking from the account's page is
  ours (`src/github-signin/link.ts`).
- `users.email` of a GitHub user is GitHub's **verified primary address** at the time the account was made, marked
  verified; the app reads it with the user token of the App (`GET /user/emails`, the account permission "Email addresses").
  It is not changed by a later sign in. The exception is the placeholder `<github id>@users.noreply.github.com` of a user the
  update imported (`users.imported_at`): the next GitHub sign in replaces it by the verified primary address when nobody else
  has it, and otherwise keeps it and records the address in `users.email_conflict` for a hint.
- The GitHub user token is kept encrypted with `APP_SECRET` by Better Auth for the accounts that sign in with GitHub; the app does
  not read it (the binding of installations asks for a fresh authorization). A linked identity (`src/github-signin/link.ts`) keeps none.
- Better Auth skips its origin and CSRF checks when `NODE_ENV` is `test`. `auth.ts` switches them
  on explicitly so the tests run what production runs.
- The pages read the session behind a `<Suspense>` boundary (Cache Components); route handlers call
  `connection()` before touching the database so `next build` never runs them.

## Rule: the proxy is not the only guard

A Server Function is a POST to the page it lives on, so the proxy lets it through when the page is
public (for example `/login`) and stops seeing it if the matcher changes. Therefore every protected
Server Function and every protected Route Handler calls `requireUser()` itself, before it touches
data. `guard-rule.test.ts` fails for a route handler that is not public, or a file of Server
Functions, that does not call it; the Server Function files that are public on purpose
(`actions.ts`: start the sign in, sign out) are listed in that test. The admin portal has its own, stricter
guard (404 for anybody who is not the instance admin, `src/admin/README.md`); its pages call
`requireAdmin()` and its data routes `lookupAdmin`, which the test accepts in place of `requireUser()`.

## Not done yet

Expired `sessions` and `verifications` rows (every `POST /api/auth/sign-in/social` writes a state
row) are never pruned. Fine for the MVP; a cleanup job belongs to the operations work (CR-40).

## Changing the Better Auth configuration

A new option or plugin can need a new column. `schema-drift.integration.test.ts` asks Better Auth
for the migration it would run; after our migrations that plan must be empty. When it is not, add a
migration to `src/db/migrations/` (never run Better Auth's own migration at start-up).
