# Testing

This file is the source of truth for how Code Reviewer is tested. A change without the tests it
requires (section 3) is not done. If code and this file disagree, fix one of them in the same PR.

Status markers: "exists" means it works in the repository today; "planned" means a later issue adds
it. Do not document planned things as if they existed in READMEs or PR descriptions.

## 1. Principles

- Test at the lowest level that can prove the behavior, and prove each behavior at one level only.
- Deterministic: no `sleep` or fixed waits (wait for the condition), time and randomness are
  injected, every test brings its own data.
- No real external service in any automated test: no real GitHub, no real LLM, no internet. External
  systems are replaced by fakes (section 5). Real model runs are manual and never part of CI.
- No silent skip. Which suite runs a file is decided by its location and name, not by a runtime
  check. A suite that needs infrastructure (Docker, Postgres) fails loudly when it is missing, it never
  skips. Known gap until `verify:structure` lands (planned): an app test file outside the Vitest
  project globs (for example `app/integration-tests/x.test.ts` without the `.integration` infix) is
  not run by any project and nothing reports it, so check the suffix rules in section 4 by hand.
  The runner side has no such gap: a pytest file outside `tests/<level>/` is a collection error.
- Never weaken, skip or delete a test to get green. Never raise retries to hide flakiness (the one
  Playwright retry on CI is the accepted baseline, it is not a place to add more). Report flaky
  tests.
- No skipped or focused tests in code: ESLint rejects `.skip` and `.only` tests in
  Vitest files (`vitest/no-disabled-tests`, `vitest/no-focused-tests`) and in Playwright files
  (`playwright/no-skipped-test`, `playwright/no-focused-test`).
- The only quarantine is for e2e journeys: a journey failing twice without a code change gets
  `@flaky` in its title in the same PR that opens a repair issue (PRs skip tagged journeys with
  `--grep-invert @flaky`, the nightly run still runs them). Unit and integration tests have no
  quarantine: fix at once, or report to the project lead; do not skip.
- Time budget: a PR CI run over 15 minutes, or a smoke run over 5 minutes, is a defect to be fixed
  like a red test.
- No coverage threshold and no coverage command for now. Add both together if the customer asks.
- No secrets in tests, logs or output. Test values are fixed dummies.

Unit means no database, no real process and no outside network. The one exception is the network
guard's own tests (app and runner): they open sockets on loopback to prove that loopback stays
reachable while everything else is blocked.

Every integration test gets a real Postgres database of its own, cloned from a migrated template in a
few milliseconds, so they are cheap and run on the host against a Postgres server (see "Integration tests and
Postgres"). The rule: anything that touches Kysely and a real database is `*.integration.test.ts`; pure
logic never opens a database.

## 3. Required tests by change type

| Change                                                          | Required                                                                                                                                 | Level                               |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| Bug fix                                                         | A test that is red before the fix and green after                                                                                        | Lowest level at which the bug shows |
| Logic: state machine, filtering, backoff, formatting            | Normal case, edge cases, failure cases                                                                                                   | Unit (app or runner)                |
| Repository, SQL or transaction (claim, lease)                   | Against real Postgres, including concurrent claim by two Workers                                                                         | App integration                     |
| HTTP route, server action, webhook handler                      | Through the real handler, including refusals: bad signature, missing or wrong token, not signed in, not on the allow list, invalid input | App integration                     |
| Auth, GitHub App credentials, tokens, anything handling secrets | Same as a route; refusal cases are mandatory; plus a test that secrets do not appear in logs or responses                                | App integration or runner unit      |
| Runner API or webhook payload shape                             | Contract test on both sides                                                                                                              | Contract                            |
| Runner process handling (spawn, timeout, kill, parallelism)     | Real subprocess with the fake PR-Agent                                                                                                   | Runner integration                  |
| New core user flow                                              | One e2e journey; `@smoke` only for a real core path                                                                                      | E2E                                 |
| PR-Agent upgrade, config or prompt change                       | Engine smoke green; note the PR-Agent version in the PR                                                                                  | Engine smoke                        |
| Purely visual change                                            | No automated test; the issue says so explicitly                                                                                          | none                                |
| Refactor without behavior change                                | No new test; all existing tests stay green                                                                                               | none                                |

- App: unit `*.test.ts(x)`, integration `*.integration.test.ts(x)`, e2e `*.e2e.ts`. E2E files never
  end in `.test.ts`, because Vitest would pick them up.
- Runner: the level of a test is its directory; `tests/conftest.py` applies the marker and rejects a
  test outside the level directories. Files are `test_*.py`.
- New top-level test folders or new `integration-tests/` categories need an agreed change to this
  file first.
- App test titles are plain English behavior sentences ("rejects a delivery whose signature does not
  match the body"): no implementation words and no issue, ADR or section identifiers. Runner test
  function names are behavior sentences too (`test_a_claimed_job_is_released_when_the_heartbeat_is_rejected`).
  E2E titles are full sentences with tags (`@smoke`, `@flaky`).
- Link a test to its test case from the issue with a comment above the test that names the issue
  number and the case id (`// #123-T03` or `# #123-T03`), so the test traces back to its issue; never
  in the title.
- Every test file starts with a short comment or docstring: which behavior it pins down and why.
- One behavior per test. Given, when, then is the shape of the body (arrange, act, assert separated by
  blank lines), not keywords in the code.
- Mocks are reset per test (Vitest `clearMocks` and `restoreMocks`; pytest fixtures are
  function-scoped by default). Use `vi.mock` or monkeypatching only for your own collaborators in unit
  tests.

Network guard (exists, applies to every automated test):

- App: `app/src/test-support/network-guard.setup.ts` is a Vitest setup file for the `unit` and
  `integration` projects. Any TCP connection (fetch, `http`, `https`, raw `net`) to a host other than
  loopback fails with the error code `NETWORK_GUARD_BLOCKED`. Extra hosts, such as a database server on
  another machine, are allowed with the comma separated `TEST_ALLOWED_HOSTS` variable.
- Runner: pytest runs with `--disable-socket --allow-unix-socket --allow-hosts=127.0.0.1,::1,localhost`
  (pytest-socket), configured in `runner/pyproject.toml`. Connections to other hosts raise
  `SocketConnectBlockedError`. DNS lookups are not blocked, but the connection that would follow is.
- The guard covers the test process only. A subprocess started by a test (for example the fake
  PR-Agent) is not guarded and must itself only talk to loopback fakes.
- The Dynamic e2e lane (`e2e-dynamic`, #253) does not rely on a guard inside a language runtime: it runs in
  a network namespace of its own whose only network is loopback, with an nft table at the output hook
  (`app/e2e/dynamic/guard.nft`) that counts and rejects every connection to anything else, per user
  (the engine user of the pinned OpenCode, the Diff job user, root, anyone else). It therefore covers
  OpenCode, Git, `rg`, Node and any helper process alike. A test fails when a counter is not zero
  (`app/e2e/helpers/dynamic-lane-guard.ts`; the journey reads it, and the lane's script reads it once more at
  the end). Positive controls (`e2e/dynamic/network-guard.e2e.ts`) make each kind of process connect to a
  reserved address and show that its counter moves, so the guard cannot pass vacuously.
  Name lookups never leave the namespace: the lane has a resolver of its own on loopback
  (`app/e2e/helpers/lane-dns-stub.ts`) that answers every name "no such name" and logs it. Because that traffic is
  loopback, `guard.nft` counts it apart (`dns-*` counters, UDP and TCP port 53, per user, #714) and the lane
  fails when the engine user sent any query, or when a name is asked that is not on the checked-in allowlist
  (`app/e2e/dynamic/dns-allowlist.txt`, each entry with the issue that explains it).

Privileged suite (`runner/tests/privileged/`, `uv run pytest -m privileged`, #197 part 2b, #244): what
only root can prove about the Dynamic runner's engine boundary. It runs **as root with the
capabilities of the hardened container spec (`contracts/worker-container.v1.json`)**, with no-new-privileges, in a network namespace with a
loopback interface and no route out and in a mount namespace laid out like the container (#249):
every disk filesystem read-only, a fresh `/run` and `/tmp` tmpfs with the options of the spec
(the container mounts nothing from the host; a CI host has a Docker socket), so the whole suite
doubles as the proof that the job directories, leases and the engine's home need no other writable
path. It has **three phases**, as the runner
has two stages of life (`PRIVILEGED_PHASE`, set by `scripts/privileged_phases.sh`;
`tests/privileged/conftest.py` fails unless the effective, permitted and bounding sets equal the
phase's):

- **startup** (`tests/privileged/startup/`): exactly what the container is created with (`CHOWN`,
  `DAC_OVERRIDE`, `FOWNER`, `KILL`, `SETGID`, `SETUID`, plus the startup-only `NET_ADMIN` and
  `SETPCAP`). It proves the rules as such (`test_network_rules.py`) and the startup step itself,
  run for real in a process of its own (`startup_process.py`, `test_startup_drop.py`): the static
  rules for the slot's fixed ports are in the kernel, and the loop, a thread started later, a job
  process and the engine user's process have no `NET_ADMIN` or `SETPCAP` in any set or in the
  bounding set, `nft` fails for the supervisor and its job processes, the probe passes, starting
  again replaces the rules instead of stacking them, and a host without `nft` still loses the
  capabilities and fails every Dynamic job closed.
- **job** (everything else): `tests/privileged/job_phase.py` runs the production startup step and
  then pytest in the same process, so the tests run as a job process sees the container: the
  capabilities are exactly the six of the supervisor, the bounding set has no `NET_ADMIN` or
  `SETPCAP`, and the rules (installed by the production code) cannot be read or changed by anyone.
  `test_read_only_rootfs.py` judges the layout: root with its capabilities cannot change `nft`, the
  runner source or the system (`EROFS`), cannot remount, the tmpfs are `noexec,nosuid,nodev` with a
  size limit, and the engine user can write nowhere but `/tmp`.
- **execve** (`tests/privileged/execve/`, `execve_phase.py`): the same startup step, started
  **without** no-new-privileges so that the bounding set is what is tested. Probes prepared by the
  script before the drop (a file-capability `cat`, one with the effective flag, a setuid-root `cat`,
  on an exec/suid tmpfs) cannot give root, the Diff job user or the engine user `NET_ADMIN` or
  `SETPCAP` back.

`scripts/run_privileged_offline.sh` arranges the namespaces and the capabilities with `sudo`,
`unshare --net --mount` and `setpriv --bounding-set`, creates the engine user (`10101`), a stranger
(`10201`) and the Diff job user (`10001`), and runs both phases; `app/src/ci/hosted-lane.test.ts`
keeps the capability list of the lane equal to the spec. It is a job of its own in
`engine.yml` (next to the two engine halves), needs `nft` (apt `nftables`), `rg` and the pinned OpenCode, and is deselected by
default. Locally without root it fails with the way to run it (never a skip); this is **CI-only for
developers without root**. It proves, against the real kernel and the real `prepared_checkout` (#196)
over real Git objects, with loopback sentinels standing in for "another job's proxy" and "an
external host", in the job phase (`test_static_rules.py`): the engine user reaches its proxy and its
own port and nothing else (TCP, UDP, another loopback address, IPv6), other users are untouched,
refused connections end in an immediate error (a refusal errno, never a timeout; the time it takes is
not asserted), a UDP flow another process opened and closed cannot be reused by the engine user, the
probe passes, and nobody (the supervisor and the engine user) can list or change the rules; no
AF_UNIX listener other than the engine's own is visible to the engine user while an engine runs,
and no Docker socket exists, with positive controls so the check cannot pass vacuously
(`test_unix_sockets.py`); the engine process is the dedicated user with its own group only, no
capability, cannot become root, read the supervisor's state or write the export, has no capability in
any set (nor `NET_ADMIN` in its bounding set) and `no_new_privs`, sees no credential, and its config
is readable by that user only and cannot be rewritten by it (`test_engine_launch.py`); a helper in a
session of its own is confined and killed with the engine, a port held by a stranger is not trusted
(the slot's engine port is fixed, so the start fails instead of moving), a tree of sticky and
unreadable directories the engine user filled is removed with the job and the lease is free again;
SIGTERM, which is how the job loop ends a job on lease loss, shutdown and timeout, ends the job, its
engine, its helper and its files (the static rules stay), and a job that was killed without cleanup
leaves processes that the loop's sweep and the next job's first step clear (`test_job_termination.py`,
`test_engine_launch.py`; the loop's sweep itself in `tests/unit/test_job_loop_engine_sweep.py`); a
root loop starts a Diff job as the job user and a Dynamic one as the supervisor, both with a bounding
set that has lost the startup-only capabilities (`test_job_users.py`); and the unmodified pinned
engine reviews a hostile repository through the whole production path as that user behind those rules
(`test_real_engine.py`). The startup self-check that advertises `opencode` (#202) is pinned at three
levels: its decisions, reasons and order with the facts injected (`tests/unit/test_dynamic_review_self_check.py`,
`test_job_loop_advertise.py`: a failed check never advertises, the default runner never passes, the
loop hands a Dynamic job process only the verified command), the real kernel, users and pinned engine
(`tests/privileged/test_self_check.py` in the job phase: the check passes and advertises; an engine
user without the network rules fails the probe; a missing user, a foreign group, a tampered binary and
another pinned version are each refused; `startup/test_self_check_capabilities.py` in the startup
phase: a process that still holds `NET_ADMIN` is refused) and the built image (below). Not covered:
a kernel without `nf_tables` beyond the fail-closed path above (no test can run there), and the
worst-case memory and OOM measurements on a real deployment target, which are a manual step
(`docs/dynamic-review.md`, "Capacity").

Privileged e2e lane (`app/e2e/dynamic/`, `playwright.dynamic.config.ts`, `make test-e2e-dynamic`, CI job `e2e-dynamic`,
#253, #201-T01): the Dynamic Review journey with nothing in the path replaced. `runner/scripts/run_dynamic_e2e.sh` fetches
the pinned OpenCode and ripgrep (`fetch_opencode.py`, `fetch_ripgrep.py`: only the bytes of the pin files), makes the one
production build of the app, and runs `runner/scripts/dynamic_e2e_namespace.sh` as root in `unshare --net --mount --pid
--fork --mount-proc`. Inside: loopback only, the network guard (above) loaded first, a default route into a veth pair
nothing answers on (so every attempt to leave reaches the guard), a fresh `/run`, the engine user 10101 and the job user
10001 in bind-mounted copies of passwd and group, the pinned tools at `/usr/local/bin/{opencode,rg}` and the pin files in
`/opt/code-reviewer/pins` (overlays: the host is not changed), then the preflight, the journeys, the guard's last word,
and a check that no process of the lane is left (the pid namespace ends whatever is). It is the Dynamic image's layout
on the host's kernel instead of the image itself, because the guard needs a network namespace the lane owns; the image
is smoke tested by `image-runner-sandbox`. The configuration has its own server list (the fake GitHub and one app over a Postgres database of its own, a
private port pair: `E2E_PORT` defaults to 3517 here, the app listens on `E2E_HOSTED_PORT` (default 3617) and the Dispatcher on the next one, never 3000 or 3100) and
its own projects: `prepare` (the first-run setup and the GitHub App of the app), `guard` (the positive controls),
`hosted` (the journey, T02 of the hosted lane below). The lane's namespace has loopback only, so the app reaches the Postgres server through a Unix socket that `e2e/pg-bridge.ts` forwards from outside the namespace (`E2E_DATABASE_URL` names the server). `playwright.config.ts` ignores `e2e/dynamic/`.

- **What keeps the lane safe, and must not change.** The job runs the code of the pull request as root (`sudo`, the
  namespace script, the Python runner, Playwright). That is acceptable only because it runs on a GitHub-hosted,
  ephemeral VM, on the `pull_request` trigger (a fork gets a read-only token), with `contents: read`, no `secrets.*`
  and a checkout with `persist-credentials: false` (the jobs of `engine.yml`, one of which runs a privileged suite, too). It
  must never move to a self-hosted runner, to `pull_request_target`, or to a job with a secret or a write
  permission: `src/ci/dynamic-lane.test.ts` (#253-C06, C07) fails if it does. Whether workflows of outside
  contributors need an owner's approval every time is a repository setting, not a file in the repository (see the
  PR #254 recommendation: "Require approval for all outside collaborators").
- **Running it locally** (`make test-e2e-dynamic`) builds as you and runs the rest as root; at the end the script gives
  every file root created in `app/` and `runner/` (test-results, playwright-report, `.next/cache`, `__pycache__`) back to
  you, however the lane ends. The fetched tools are copied to the lane's own root-owned tmpfs before they are installed;
  the pin check (size and SHA-256 in the fetch scripts, the preflight and the runner's self-check) is what accepts
  them.
- **Preflight** (`app/e2e/helpers/dynamic-preflight.ts`, a command run by the script and the global setup of the
  configuration): the pinned OpenCode and `rg` where the image has them, `nft` (it must list the ruleset), the engine
  user with a group of its own, and root. Every missing item is named, all of them at once, and the run stops; nothing
  is skipped. One unit test per item (`src/test-support/dynamic-lane-preflight.test.ts`).
- **The Worker** is started by the real Dispatcher's Sandbox-Launcher through the `docker` stand-in, which calls `runner/scripts/dynamic_e2e_worker_container.sh`: root, exactly the `cap_add` of the hardened container spec through `setpriv --bounding-set`, `--no-new-privs`, a read-only root and the container's `/tmp`. The journeys are in `e2e/dynamic/hosted-dynamic.e2e.ts` (one serial group; T02 of the hosted lane below, then T01 and T09). Its setup turns the Dynamic Review gate on in the lane's own database through the admin API (it is off in every shipped configuration) and chooses Dynamic Review for the project. `stop()` fails when a process of the engine user is left.
- **T02** (hosted lane below): the deploy canary, a signed `opened` event, and the real OpenCode reads a file the diff does not touch (the fake LLM's agent script, `scriptAgent`); one summary comment lands, the Worker's log says `opencode is advertised` (the startup self-check on its own merits, #253-L01, which the single-process lane's journey used to read from the runner's output), and neither a key nor a token is in the page, the Dispatcher's output, the Worker's records or what the model was shown.
- **T01** (`#201-T01`, same file): the same chain on a pull request of its own, then the Runs page shows kind, model, usage (tokens and calls from the proxy, read from the run's data route) and the link, the Findings show the finding of the comment, and a fix is pushed: the same comment is edited and lists the finding as resolved (a second Worker, a second real engine run). No key or token is in the page, the runs API, the Dispatcher's output, the Workers' logs or what the model was shown, and no engine process is left.
- **T09 of #299** (same file): a pull request whose head the fake GitHub does not advertise fails the real preparation (`checkout_incomplete`, reason `ref_moved`); the Runs page says Failed and the pull request holds exactly one comment, the failure note of the bot with the code, the reason and the head, and nothing of the title, the description, a file name or a credential. Where the note is written, what it holds and what it never holds are proven at lower levels (`runner/tests/unit/test_dynamic_review_failure_note*.py`, `runner/tests/integration/test_dynamic_review_job.py`).
- Fakes the lane added: the fake GitHub serves Git over smart HTTP (`fakes/github/git-http.ts`, repositories made with
  `fakes/github/git-fixture.ts`, registered through `POST /__fake/git-repositories`), and the fake LLM can answer as the
  model of an agent (`scriptAgent`), tests in `src/integrations/providers/github-app/fake-github-git.integration.test.ts`
  and `src/test-support/llm-fake-agent.integration.test.ts`.
- What it does not cover: a real model, a real GitHub, the Docker image itself (`image-runner-sandbox` and `sandbox-local` do), worst-case memory, and the operational
  items on a staging instance (#250 review: T07, T10).

Hosted e2e lane (`app/e2e/hosted/`, `playwright.hosted.config.ts`, `make test-e2e-hosted`, CI job `e2e-hosted`, #332): the
hosted flow of umbrella #316 with nothing of ours replaced. The app runs as a serverless deployment does (
a production build, Postgres: the lane makes its own database on the server of `E2E_DATABASE_URL`, runs `pnpm migrate`, and sets the
instance up with the code of `pnpm setup-code`), in the dispatch mode (`RUNNER_DISPATCH=webhook`). The journeys start the real

out of its environment (it serves Diff jobs); the container's own startup is proven by the privileged lane below and by `sandbox-local`.

- **Time.** The app is a separate process, so its clock cannot be injected, and the waits the journeys are about are minutes long.

  cron does every minute. No journey sleeps, and no other row is ever written.

### Integration tests and Postgres

- A Postgres server is required and the tests fail, naming it, when it is not there; they never skip.
  `TEST_DATABASE_URL` names it (CI starts a `postgres:18` service container; locally, a throwaway container on a
  private port, for example `docker run -d --name cr-pg -p 127.0.0.1:54399:5432 -e POSTGRES_PASSWORD=postgres postgres:18`
  with `TEST_DATABASE_URL=postgres://postgres:postgres@127.0.0.1:54399/postgres`; the default is
  `postgres://postgres:postgres@127.0.0.1:5432/postgres`). The user needs to create and drop databases. The URL must
  point at loopback (`127.0.0.1`) so the network guard allows it. Remove the container when you are done.
- `src/test-support/db-template.global-setup.ts` (the `integration` project's global setup) creates one template
  database, runs all migrations into it and drops it at the end of the run.
- `createTestDatabase()` (`src/test-support/test-database.ts`) clones the template (`create database ... template ...`)
  into a database of its own per test, opens it through the production `openPostgresDatabase`, and drops it and closes its
  connections after the test (`track()` and `cleanUpAfterTest()` do the same for tests that open their own).
  `createPostgresTestDatabase()` (`src/test-support/postgres-test-database.ts`) is the older name of the same helper and
  `connectPostgres()` opens a second connection to the same database for two-instance tests. No two tests, files or workers
  share a database. The plain server helpers (`postgresTestUrl`, `adminPool`, `newDatabaseName`) live in
  `src/test-support/postgres-server.ts`, which imports no test framework, because the global setup uses them too.
- `createAuthHarness()` (`src/test-support/auth-harness.ts`) adds the rest of a sign in setup on top of `createTestDatabase()`: the app's real Better Auth instance (`createAuth`), the fake GitHub on a loopback port (`startTestGithub()` in `src/test-support/github-fake.ts`, the one fake of the app's tests; `createAuthHarness({ github })` and `startGithubAppHarness({ fake })` can share one instance), and helpers that walk the OAuth flow with a cookie jar and call `auth.handler` with real `Request` objects. Session expiry is tested by moving `Date` with `vi.useFakeTimers({ toFake: ["Date"] })`. The harness takes the sign-up rule (`signUpRule`), whether mail can be sent (`mailConfigured`) and the ways to sign in that are on (`signInMethods`), and `restart({...})` starts the same database and fake GitHub again with other settings, like a server restarted after the admin changed them.
- `createWorkspaceHarness()` (`src/test-support/workspace-harness.ts`) is a test database with a clock the test moves, a mail double, the real counters and the real services and route handlers of the workspaces (`assembleWorkspaces`): `addWorkspace`, `addMember`, `addUser`, the tokens that were made, what was logged. The route files are driven with `signedInMember()` (`src/test-support/session-lookup.ts`), which makes an account and its membership and hands back the session lookup that the test puts in place of the real one.
- A second connection or a second app instance is a real child process (`db-process.ts` runs `db-child.ts`), so that a lock or a
  transaction held by one cannot be released by the test process itself. Node runs `db-child.ts` directly (type stripping), so
  files it imports from `src/db/` use relative imports with a `.ts` extension and no TypeScript-only runtime syntax (enums,
  parameter properties); `erasableSyntaxOnly` in `tsconfig.json` enforces the latter.
- The job queue tests use `createJobQueueFixture()` (`src/test-support/jobs.ts`): a migrated database
  with one integration and two repositories, and a clock the test moves by hand (leases and timeouts
  are tested by advancing it, never by waiting). Callers that must overlap are real processes
  (`jobs-child.ts`, started together by a barrier, with the queue's clock fixed to a given time).
- Tests of file system errors that depend on permissions (a read-only directory) hold only for a
  non-root user, because root may write anywhere. Such a test is registered with `itNeedsNonRoot`
  (`src/test-support/root-only.ts`), which skips it with that reason when the suite runs as root
  outside CI and fails instead of skipping when CI is set. Every skip prints one line with the
  reason to stderr, and `--reporter=verbose` lists them too. Run the suite as a normal user.

`make test-engine` runs the engine suite on your machine (after priming the tiktoken cache, see above; without the network namespace, which is Linux and CI only).

## 8. CI

`development` and `main`. A new push to a pull request cancels its
superseded run. A run for a push is never cancelled or replaced: the concurrency group of a push
contains the commit hash, so every pushed commit gets its own run. No repository secrets in test jobs, the token is
limited to `contents: read` (the `changes` job also reads pull requests for the path filter), every job has a
timeout, GitHub's own actions are pinned to a major version, every other action and the actionlint Docker
image to a commit hash or image digest, and the uv version is pinned. The structure of the

### Dependency license check

`license-policy.json` (repository root) holds the allow list of SPDX license ids, the exceptions (a package, matched by exact name or a name ending in `*`, may carry the listed licenses) and the packages that the lockfiles list for other platforms but that are not installed everywhere (`notInstalled`, with the license that the registry declares). `app/src/ci/license-check/` reads it:

- `collect.ts` gathers the installed packages (`pnpm licenses list --json`; `runner/scripts/list_licenses.py`, which prints the `METADATA` of what uv installed) and the packages of `pnpm-lock.yaml` and `uv.lock`. All of it is local, nothing is fetched.
- `python-license.ts` turns Python's three ways of naming a license (expression, free text, trove classifiers) into one SPDX expression; `spdx.ts` reads expressions (`OR` needs one allowed side, `AND` needs both).
- `check.ts` judges: a license outside the allow list and not granted to the package by name fails; a lockfile package that is not installed and not declared in `notInstalled` fails (its license cannot be read); an exception that matches no lockfile package fails (so the list shrinks with the dependencies).
- `binaries.ts` audits the prebuilt binaries of the Dynamic runner image (the `binaries` list of the policy: OpenCode and ripgrep), offline, from their pin files (`runner/opencode-pin.json`, `runner/ripgrep-pin.json`). It fails (`BINARY_*` codes) when a pin file is missing or unreadable, when its `repository` or `licenseUrl` is missing, when its license is not on the allow list or differs from the policy entry (version, source commit and license must agree), when a pinned platform lacks a SHA-256 (64 hex digits) for the archive or the executable, or when `THIRD_PARTY_LICENSES.md` or `NOTICE` does not name the binary, its version and its source commit in one entry. OpenCode is a Bun-compiled executable whose bundled npm packages the other collectors cannot see, so the check also reads the reviewed snapshot `runner/opencode-bundled-licenses.json` (`BUNDLED_SNAPSHOT_*` codes: unreadable, or generated for another commit than the pin) and judges every package of it like a dependency (ecosystem `bun`: allow list, exceptions, stale exceptions). The snapshot is an upper bound (a superset of what Bun embedded), written by `runner/scripts/audit_opencode_bundle.py --fetch` (a person, with the internet, when the pin changes; the script refuses the network without `--fetch` and its unit tests inject the fetcher, `runner/tests/unit/test_audit_opencode_bundle.py`). A package that declares no license is recorded as `NONE` and fails the check until someone decides. `binaries.test.ts` covers the rules with made-up pins, documents and snapshots.
- `THIRD_PARTY_LICENSES.md` has the same allow list and the same tables, and the table of binaries; `policy-doc.test.ts` fails when they differ, `policy.test.ts` checks the policy against the real lockfiles, `check.test.ts` and `cli.test.ts` cover the rules with made-up packages (an unlisted copyleft dependency exits with 1).

### SPDX headers

`app/src/ci/spdx-headers/` holds the rules (`rules.ts`: which files are source files, the comment syntax per language, how the header is added without moving a shebang or a Dockerfile `# syntax=` line), the command that writes and checks the headers (`cli.ts`: `pnpm spdx:add`, `pnpm spdx:check`, `make fix-spdx-headers`) and the tests. `spdx-headers.test.ts` lists every file that git tracks or would track and fails for each source file without `SPDX-License-Identifier: LicenseRef-Proprietary` in its first lines. One rule (`headerProblem` in `rules.ts`) serves the test and the command: a file with another identifier (`SPDX-License-Identifier: MIT`) fails the check too, and `pnpm spdx:add` reports it and leaves it alone, because another license is a decision for a person. `rules.test.ts` and `cli.integration.test.ts` cover the rules and the command with made-up files. After merging a branch that predates the rule, run `make fix-spdx-headers` and commit the result.

## 9. Test cases in GitHub issues

Every issue that changes behavior has a "Test cases" section: one row per behavior with id (T01, T02, ...), type (happy, error, edge,
security), level, given, when, then. Cases are written when the issue is refined. The PR description
maps every case of the issue to a test file and name, or to "manual" or "not applicable" with the reason (a rule for
maintainers and agents; the table is optional for outside contributors). Every
issue covers: the happy path, every error it can produce, edge cases (empty, maximum, duplicates and
replays, ordering and concurrency, expiry, idempotency, large diffs, fork and draft PRs), security
cases whenever auth, webhooks, the runner API, tokens or user input are touched (secrets must not
appear in logs, responses or PR comments; PR content is data and never changes runner commands or
prompt instructions), and a regression case for every bug.
